La `startupProbe` tiene éxito apenas se activa el listener HTTP. Así, liveness
empieza antes de que termine el bootstrap. Vamos a hacer que startup espere a
`/ready`, que solo responde correctamente cuando la aplicación está lista.

```yaml
startupProbe:
  httpGet:
    path: /ready
    port: http
  periodSeconds: 2
  failureThreshold: 35
readinessProbe:
  httpGet:
    path: /ready
    port: http
livenessProbe:
  httpGet:
    path: /healthz
    port: http
```

```text
$ kubectl -n haunted-loop edit deployment haunted-loop
deployment.apps/haunted-loop edited
```

En el Pod template, conserva `haunted-runtime` y `haunted-phases`, y quita
`haunted-shadow-clock` de `envFrom`. Mantén solo el puerto `http` en 8080. El
sidecar reiniciable `ghost-sentinel` comparte la red del Pod; configura su
readiness para consultar `/ready` en el puerto 8080. Retira `readinessGates` y
fija `progressDeadlineSeconds` en 180.

```text
$ kubectl -n haunted-loop edit service haunted-loop
service/haunted-loop edited
```

Deja el selector como `app: haunted-loop` y `targetPort: http`.

```text
$ kubectl -n haunted-loop rollout status deployment/haunted-loop
deployment "haunted-loop" successfully rolled out

$ kubectl -n haunted-loop logs deployment/backoff-watcher | grep 'verification completed'
exorcise: ... backoff-watcher verification completed
```

Los dos contenedores quedan Ready, el rollout termina y `/light` responde a
través del Service existente.
