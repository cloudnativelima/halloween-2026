El Service selecciona ambos backends y resuelve el puerto nombrado para cada
Pod. En stable, `web` apunta al listener de negocio; en canary, al de
diagnóstico. Vamos a corregir la declaración de puertos de canary y quitar las
sobrescrituras que alteran el contrato de negocio o bloquean readiness.

```text
$ kubectl -n cursed-endpoints edit deployment spectral-stable
deployment.apps/spectral-stable edited
```

En stable, conserva `BACKEND_TRACK` y configura `envFrom` para cargar
`seal-contract`. Quita `BUSINESS_STATUS`, `CONTRACT_STATUS` y la readiness gate
sin controlador.

```text
$ kubectl -n cursed-endpoints edit deployment spectral-canary
deployment.apps/spectral-canary edited
```

En canary, conserva `BACKEND_TRACK` y el `envFrom` de `seal-contract`; quita la
variable `BUSINESS_SEALED` del Downward API y la fuente `seal-legacy-profile`.
Configura los puertos y readiness así:

```yaml
ports:
  - name: web
    containerPort: 8080
  - name: admin
    containerPort: 9090
readinessProbe:
  httpGet:
    path: /ready
    port: web
```

```text
$ kubectl -n cursed-endpoints edit service cursed-api
service/cursed-api edited
```

El Service principal debe omitir `publishNotReadyAddresses` o dejarlo en
`false`. Conserva su selector y la afinidad `ClientIP`.

```text
$ kubectl -n cursed-endpoints rollout status deployment/spectral-stable
deployment "spectral-stable" successfully rolled out

$ kubectl -n cursed-endpoints rollout status deployment/spectral-canary
deployment "spectral-canary" successfully rolled out

$ kubectl -n cursed-endpoints logs deployment/endpoint-watcher | grep 'verification completed'
exorcise: ... endpoint-watcher verification completed
```

El log de `endpoint-watcher` confirma la respuesta de ambos tracks y del Service
principal. `/seal` devuelve `status: complete` y `sealed: true` desde cada
backend.
